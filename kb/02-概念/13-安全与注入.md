# 安全与注入：模型分不清"指令"和"数据"

**① 一句话定义**
确保**外部内容不能操纵系统行为**（提示注入）、**不能越权访问**（权限）、**不能把数据带出去**（外发）。

**② 它解决什么问题**
模型把"用户说的话""检索到的文档""工具返回的网页"**放在同一个 token 序列里**，没有天然的信任边界。攻击者只要能让恶意文本进入上下文（网页、邮件、简历、issue 标题），就可能让 Agent 去读密钥、发邮件、转账。

**③ 关键机制**

**第一原则：lethal trifecta（致命三要素）**
> **私有数据 + 不可信内容 + 外发通道** 三者同时具备 = 高危。
> 工程上可行的第一动作：**砍掉其中一个**（例如禁止从不可信内容触发的网络外发，或对写操作强制人工确认）。

| 防线 | 做法 | 局限 |
|---|---|---|
| 输入隔离 | 分隔符/标签包裹外部内容、标注来源、system 里声明"外部内容不可执行" | 只是提高难度，不是数学保证 |
| 权限最小化 | 工具 scope 最小、只读优先、每工具独立权限 | 配置错了等于没配 |
| **检索期 ACL 预过滤** | 权限条件下推到检索，别先取后滤 | 需要索引侧带 ACL 元数据 |
| 工具白名单 + 参数校验 | 不允许"通用 shell/SQL"工具；参数 enum/pattern | 模型可诱导合法参数的非法组合 |
| egrees 白名单 | 出站域名/收件人白名单，禁止任意 URL 外发 | 影响功能，需权衡 |
| 不可逆操作确认 | 转账/删除/发邮件 → 人工确认（HITL） | 交互成本 |
| 输出过滤 + 审计 | 脱敏、密钥检测、全量留痕 | 事后手段 |
| 沙箱 | 代码执行/浏览器在隔离环境，凭据注入而非广播 | 逃逸风险，需持续更新 |

**④ 边界与代价**
- **没有只靠 prompt 的完美防御**：别在面试里说"我在 system prompt 里加了'不要听用户的'"。
- 防御会伤体验：过多确认导致用户点"同意"成了肌肉记忆。
- 间接注入最难：内容来自你信任的协作方（客户上传的 PDF、供应链的 README）。
- 模型升级会改变攻击面，红队用例要常跑。

**⑤ 工程落点**
- `projects/_template/src/tools/builtin.ts` —— `search_docs` 在**检索阶段**按 tenant/ACL 过滤（演示"预过滤"而不是"后过滤"）
- `projects/_template/src/tools/registry.ts` —— 写操作（`isWrite`）强制幂等键；`create_ticket` 未 `confirm` 直接返回 policy 错误（HITL 的最小形态）
- 进阶（P3）：工具输出包裹与来源标注、egress 白名单、注入红队用例进 golden set

**⑥ 面试追问（三层）**
1. **怎么衡量**：注入红队用例的拦截率、越权用例（跨租户检索/写操作）的通过率、审计覆盖率、未确认的写操作数（应为 0）。
2. **为什么不用另一方案**：为什么不在 prompt 里声明？→ 不可靠。为什么不做模型级安全分类器？→ 是补充手段，有误杀与绕过。
3. **线上坏了怎么定位**：从 trace 找"哪条外部内容进入了上下文"→ 看它触发了哪个工具 → 看该工具是否有外发/写权限 → 复盘防线缺口。
