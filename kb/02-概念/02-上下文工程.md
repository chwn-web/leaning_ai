# 上下文工程：放什么、放哪、什么时候丢

**① 一句话定义**
在有限窗口里，**决定哪些信息进入模型、以什么顺序进入、什么时候被压缩或丢弃**的工程——目标不是塞满窗口，而是让"当前这一步决策所需的信息"处在最有效的位置。

**② 它解决什么问题**
2023 年大家都在调 prompt 文案；后来发现效果差异的大头在**给了什么信息**（检索结果、工具返回、历史状态），而不是措辞。窗口变大后问题没消失，反而变成"信息多了以后模型更糊涂"。

**③ 关键机制**

| 机制 | 做法 | 为什么有效 |
|---|---|---|
| 分层 | 稳定层（system/工具/schema）→ 任务层（目标/约束）→ 状态层（进度/工作笔记）→ 证据层（检索片段）→ 对话层 | 稳定层在前可选命中 prefix cache，还能让模型区分"规则"和"数据" |
| 位置 | 关键指令与关键证据放首尾，中间放次要材料 | lost in middle：中间位置召回显著弱 |
| 压缩 | 摘要 + **结构化工作笔记**（已完成/待办/已确认事实/悬而未决） | 纯摘要会丢数字、引用、归属；结构化笔记实测省 40–60% token 且更稳 |
| 隔离 | 工具结果、网页内容用分隔符包裹并标注来源 | 让模型能区分"用户要求"和"外部数据"，是防注入的第一道（参见 [13-安全与注入](13-安全与注入.md)） |
| 缓存 | 前缀稳定 + 变体放尾部 | 命中缓存可显著降 TTFT 与成本 |

**④ 边界与代价**
- **压缩本身会腐化**：压到第 12 轮时日期、数字、引用归属悄悄漂移，而且不报错。对策：压缩后重放关键约束 + 保留 `docId/span` 而不只是文字 + 压缩结果做一致性校验。
- 长上下文不能替代检索：塞 20 篇文档的成功率通常低于精准检索 3 篇。
- 上下文工程没有"最优解"，只有"对当前任务的可测最优"——**必须用 eval 比，不能凭感觉**。

**⑤ 工程落点**
- 现在：`projects/_template/src/agent/loop.ts` 的消息累积就是最朴素的上下文装配
- 未来（P2/P3）：`src/context/assembler.ts`（分层装配）、`src/context/compactor.ts`（结构化笔记压缩）
- 可观测：把"每轮输入 token 数 + 各层占比"写进 span，才能看出是哪一层在膨胀

**⑥ 面试追问（三层）**
1. **怎么衡量**：同一任务集下比"成功率 / 平均输入 token / 成本 / 第 N 轮后的成功率衰减曲线"。
2. **为什么不用另一方案**：为什么不做纯摘要？→ 丢引用与数字、不可追溯。为什么不直接上 1M 窗口？→ 成本、KV cache 显存、context rot。
3. **线上坏了怎么定位**：看"第几轮开始答非所问"—如果是固定轮次，是压缩腐化；如果与文档长度相关，是位置效应；如果与话题相关，是检索层问题。
