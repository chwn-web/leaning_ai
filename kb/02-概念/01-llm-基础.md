# LLM 基础：token、采样、窗口、成本

**① 一句话定义**
LLM 是一个"给定前文，预测下一个 token"的函数——**输入和输出都是 token，注意力对全文两两相连**，所有工程约束（成本、延迟、长上下文失效、不可复现）都从这两点推出来。

**② 它解决什么问题**
在它之前，每个任务要写规则或训专用模型；现在一个接口能覆盖开放式任务。代价是**输出是概率分布采样出来的，不是确定的值**。

**③ 关键机制（每条都要能推出一个工程约束）**

| 机制 | 事实 | 推出的约束 |
|---|---|---|
| Token 化 | 计费与窗口都按 token；中文/代码/JSON 的 token 效率差异很大 | 成本按"输入 token + 输出 token"两笔账算；不能按字符数估 |
| 采样 | temperature / top_p / top_k 控制随机性 | **temperature=0 也不可复现**：浮点非结合、batch 组合、MoE 路由、并发都会让结果变 |
| 注意力 O(n²) | 上下文翻倍，注意力计算量约 4 倍 | 长上下文首先是延迟问题，其次才是成本问题 |
| KV cache O(n) | 显存 ≈ `2 × batch × layers × hidden × seq × 字节数`（GQA 按 KV 头数再缩） | 并发 × 长上下文会先爆显存；这是"为什么长上下文不能免费"的根因 |
| 窗口 ≠ 有效窗口 | 首尾强、中间弱（lost in middle, arXiv 2307.03172）；输入越长性能非均匀下降（context rot） | 关键约束放首尾；长文档拆分而非硬塞；**必须在目标长度上做 eval** |
| 流式 | 首 token 延迟（TTFT）与整体延迟是两件事 | 体验优化先优化 TTFT；prompt cache 命中直接降 TTFT |

**④ 边界与代价**
- 不擅长：精确算术、实时事实、超长程一致推理、严格格式约束（没有工具时）。
- 用它的代价：延迟（数百 ms 到数十 s）、成本（按 token 线性）、不确定性（需要评测兜底）、版本漂移（供应商随时更新模型）。
- 型号选择的唯一可靠办法：**自建 100–300 条 golden 集**，测成功率/格式/工具调用/成本/延迟，公开榜只做初筛。

**⑤ 工程落点**
- `projects/_template/src/llm/provider.ts` —— Provider 接口、价格表、`withRetry`（只重试 transient）
- `projects/_template/src/core/budget.ts` —— 步数/花费/墙钟三重预算，**模型能跑多久由你决定，不是由模型决定**
- `projects/_template/src/core/types.ts` —— `Usage{inputTokens,outputTokens,costUsd}`，成本从第一天就记账

**⑥ 面试追问（三层）**
1. **怎么衡量**：TTFT / p95 延迟 / 每任务 token 与成本 / 目标长度上的任务成功率；报数要带样本量和置信区间。
2. **为什么不用另一方案**：为什么不用更长的窗口硬塞？→ 成本与质量双输（context rot + KV cache 显存）。为什么不上微调？→ 知识会变时微调不划算。
3. **线上坏了怎么定位**：先看 usage 与 TTFT 是否突变（供应商/路由/缓存命中），再看输入长度分布是否漂移，最后比对模型版本是否被静默升级。
