# 多智能体：先证明单 Agent 不够，再谈分工

**① 一句话定义**
多个带**独立上下文**的 agent，通过结构化交接协作完成一个任务。它解决的核心问题不是"能力不够"，而是"上下文装不下 / 要并行 / 要独立验证"。

**② 它解决什么问题**
单 agent 长任务里上下文会膨胀、角色会混淆、注意力被冲淡。分工看起来能解决——但**协调成本常常高于收益**，这是最容易过度设计的地方。

**③ 关键机制**

| 机制 | 要点 |
|---|---|
| 值得上的三个理由 | ①上下文隔离（每个子任务只带自己的材料）②并行（互不依赖的子任务）③独立验证（批评者/审稿者） |
| 不值得的理由 | 只是为了"看起来更专业"、任务本身线性、预算敏感 |
| 交接必须结构化 | handoff 用 JSON schema：目标、约束、已完成、引用（带 docId/span）、禁止事项。**只传摘要会让引用和约束在传递中丢失**（实测 5 条引用传到下游只剩 4 句摘要） |
| 失败主因是协调 | 多 agent 系统失败中约 **79% 源于协调**（规格不清、信息丢失、互相等待），而不是单个 agent 能力不足 |
| 甜点区 | **2–3 个 specialist** 通常最优；5 个以上往往更差、更贵、更难调 |
| 验证要独立 | 同模型自评容易趋同；"互相同意"不等于"已验证"，要么换模型、要么用规则/工具校验 |

**④ 边界与代价**
- 成本与延迟按 agent 数量放大（不是线性，因为有协调回合）。
- 状态一致性：并行 agent 改同一份状态 → 冲突与覆盖。
- 可观测性变差：一个用户请求变成多条 trace，必须靠 traceId 串起来。
- 拓扑选择（主管/对等/流水线）比"用几个 agent"更影响成败。

**⑤ 工程落点**
- 现在 `projects/_template` 是单 agent；多 agent 在 **P3 平台**（W16–W18）落地
- 届时新增：`src/agent/supervisor.ts`（路由与预算分配）、`src/agent/handoff.ts`（结构化交接契约）、`src/obs/trace-linker.ts`（跨 agent 串 trace）
- 判据：**加一个 agent 前，先写清"它解决的是上下文隔离还是并行还是验证"**，写不出来就别加

**⑥ 面试追问（三层）**
1. **怎么衡量**：同一任务集下多 Agent vs 单 Agent 的成功率/成本/延迟/p95 步数；交接错误率（下游拿到上游结论的完整率）。
2. **为什么不用另一方案**：为什么不用一个 agent 加更多工具？→ 工具数是瓶颈（>10 不稳），且上下文会混。为什么不用 workflow 串起来？→ 子任务边界不清、需要模型自己决定时 workflow 写死不了。
3. **线上坏了怎么定位**：先看是哪一段交接丢信息（对比上下游输入输出），再看是否有 agent 在等对方（死锁），最后看预算分配是否让某个 agent 提前被截断。
