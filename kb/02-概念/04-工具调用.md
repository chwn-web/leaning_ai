# 工具调用：模型只负责"想"，执行与安全是你的责任

**① 一句话定义**
工具调用是一份**双向契约**：模型输出 `{name, args}`，运行时校验后执行，再把结果作为 observation 回填——**模型不执行工具，也不保证参数合法**。

**② 它解决什么问题**
没有工具，模型只能"说"；有工具，模型能查数据、改状态、触发流程——同时也就获得了**改真实世界的能力**，所以这一层是安全事故与幻觉的高发区。

**③ 关键机制**

| 机制 | 做法 | 不这么做会怎样 |
|---|---|---|
| 数量控制 | 单 Agent 2–5 个工具；>10 个行为明显不稳 | 选错工具、参数串味 |
| 描述即文档 | 名称/描述/每个参数都像给初级开发写 docstring：用途、单位、格式、边界、示例 | 模型靠猜，参数幻觉 |
| 参数收紧 | 枚举、`minimum/maximum`、`pattern`、必填标记 | 编造订单号/优先级（P2） |
| 三层校验 | schema → 业务规则 → 权限/租户 | 非法请求直达生产库 |
| 结果回填 | 错误要**结构化且人类可读**（字段名 + 原因），让模型能改计划 | 模型重试同样的错 |
| 结果即不可信 | 工具返回的网页/文档内容当数据，不当指令 | 间接注入（P14） |
| 写操作 | 幂等键 + 二次确认 + 可补偿 | 重试导致重复下单/重复退款（P15） |
| 超时与并行 | 每个工具独立超时；同一步多个调用并行 | 一个慢工具拖死整轮；串行让延迟叠加 |

**④ 边界与代价**
- 工具越多越不稳；工具描述越长越贵（每次请求都带 schema）。
- 工具结果太长会挤爆上下文——**要在 registry 层截断/摘要**，而不是指望模型自己忽略。
- 工具描述本身可被注入（恶意 MCP server 在 description 里藏指令，见 [12-mcp](12-mcp.md)）。
- 模型"调用成功"不代表"业务正确"，业务校验不能省。

**⑤ 工程落点**
- `projects/_template/src/tools/registry.ts` —— 注册/校验/执行/重试/超时/幂等键强制，**校验失败返回 observation 而不是抛异常**
- `projects/_template/src/tools/builtin.ts` —— 三个示范工具：`calculator`（纯函数）、`search_docs`（读 + ACL 预过滤）、`create_ticket`（写 + 幂等 + 需确认）
- `projects/_template/src/core/validate.ts` —— 手写 schema 校验

**⑥ 面试追问（三层）**
1. **怎么衡量**：工具选择准确率、参数校验通过率、工具成功率、平均调用次数、错误类型分布。
2. **为什么不用另一方案**：为什么不用"让模型输出 shell 命令"？→ 权限与爆炸半径不可控。为什么不做成一个大而全的工具？→ 参数空间太大，模型选不中。为什么不直接把工具结果拼进 prompt？→ 工具结果当数据要标注来源，否则注入。
3. **线上坏了怎么定位**：先看校验失败率（是模型在编参数还是描述没写清）→ 再看业务失败率（参数对但值不存在）→ 最后看工具超时/限流。
