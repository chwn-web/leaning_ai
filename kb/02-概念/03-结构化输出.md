# 结构化输出：JSON 合法 ≠ 语义正确

**① 一句话定义**
让模型的输出**机器可解析、业务可接受**的工程——它有三层保证：语法层（是合法 JSON）、结构层（符合 schema）、语义层（字段值在业务上成立）。

**② 它解决什么问题**
早期用正则从自然语言里抠字段，脆得一碰就碎；后来只要求"输出 JSON"，又常遇到 ```` ```json ```` 包裹、多个对象、末尾截断、字段名自己发明。结构化输出把这些不确定性收敛成**可校验的契约**。

**③ 关键机制**

| 层 | 手段 | 保证什么 | **不保证什么** |
|---|---|---|---|
| 语法 | JSON mode / 约束解码 | 可 `JSON.parse` | 内容对不对 |
| 结构 | JSON Schema / function calling 的 schema | 字段齐、类型对、枚举在范围内 | 值是否真实 |
| 语义 | 业务校验 + 二次确认 + 事实核对 | 订单号存在、枚举合法、金额非负 | 跨系统一致性 |
| 修复 | 解析错误 **回填给模型** 让它重发（附具体字段名） | 自愈率显著提升 | 无限重试（要设上限） |

**④ 边界与代价**
- **"JSON 模式"只保证语法**。它会为了凑格式编一个值——所以枚举、`pattern`、`min/max` 越严，幻觉越少。
- 约束解码会增加延迟，且强约束下模型可能"填垃圾凑结构"。
- 流式场景：工具调用的参数必须**缓冲完整 JSON 再解析**，否则半截字符串会解析失败或被当正文吐给用户（P9）。
- 幻觉不是格式问题：模型不知道你的订单号，只能编 → **先查后写、写前校验、不可逆操作人工确认**。

**⑤ 工程落点**
- `projects/_template/src/core/validate.ts` —— 手写 schema 校验器（类型/required/enum/min/max/pattern/多余字段）
- `projects/_template/src/tools/registry.ts` —— 校验失败**不抛异常**，而是返回 `ok:false, errorKind:"validation"` 并把 `字段名: 原因` 回填成 observation
- `projects/_template/src/llm/provider.ts` —— `arguments` 解析失败时保留原始串，不吞错

**⑥ 面试追问（三层）**
1. **怎么衡量**：解析成功率、schema 校验通过率、修复后通过率、字段级准确率（不只整体成功率）。
2. **为什么不用另一方案**：为什么不用纯 prompt 约束？→ 模型会漂移。为什么强约束还不够？→ 语义层不在模型掌控内，业务校验必须自己做。
3. **线上坏了怎么定位**：先看是解析失败（截断/包裹）还是校验失败（字段错）还是业务失败（值不存在）——三类分别对应缓冲、schema、服务端校验。
