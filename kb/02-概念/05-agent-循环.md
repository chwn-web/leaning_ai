# Agent 循环：难的不是"能跑"，是"一定会停、停了能恢复"

**① 一句话定义**
Agent = **模型 + 工具 + 循环 + 状态**。相比一次问答，它多出来的能力是"根据中间结果决定下一步"，多出来的风险是"步数不封顶、错误会累积"。

**② 它解决什么问题**
工作流时代要把每条分支写死，长尾需求永远覆盖不完；循环让模型自己决定路径，用一套代码覆盖开放式任务。代价：**成本、延迟、可预测性全部交给运行时去控**。

**③ 关键机制**

| 机制 | 具体做法 |
|---|---|
| 三种形态 | **ReAct**（思考↔行动交错，灵活但短视）／**Plan-and-Execute**（先分解再执行，长任务强，但必须支持 replan）／**状态机**（状态显式，可持久化、可恢复、可测试） |
| 四个停止条件 | 模型返回 `stop` ／ 步数上限 ／ 预算（钱/时间）上限 ／ **动作签名重复检测**（同一工具+同一参数第 3 次出现 → 死循环） |
| 进展校验 | 每一步要求"可验证的进展"（新证据、状态变更、错误变化），否则就是在绕圈 |
| 错误分诊 | transient → 指数退避重试；permanent/validation → 回填错误让模型改计划；permission/policy → 停手交人 |
| 检查点 | 长任务把"已完成/待办/已确认事实"存成结构化状态，失败后从检查点恢复，而不是从头再来 |
| 并行与截断 | 一步内多工具并行，但限制单步调用数（防止一次吐 20 个调用把链路打爆） |

**④ 边界与代价**
- **不该用 Agent 的场景**：路径完全固定、一次检索就够、成本/延迟敏感、操作不可逆且没有审核环节、无法构造评测。
- 循环越长，单步 5% 的失败率会复利成整条链路的崩盘——所以要报 **pass^k（k 次都成功）**，而不是 pass@k。
- Agent 的调试成本远高于 workflow：同样的输入可能走不同路径 → **必须有 trace，且能回放**。

**⑤ 工程落点**
- `projects/_template/src/agent/loop.ts` —— 有界循环：`budget.step()`、动作签名 Set、`maxToolCallsPerStep`、错误→observation 回填、四种退出状态（`done / budget / loop_detected / error`）
- `projects/_template/src/core/budget.ts` —— 三重预算
- `projects/_template/src/obs/tracer.ts` —— 每步一个 span，失败时能看出停在哪一步

**⑥ 面试追问（三层）**
1. **怎么衡量**：任务成功率（pass^k）、平均步数、单任务成本、循环触发率、人工接管率。
2. **为什么不用另一方案**：为什么不直接用 workflow？→ 长尾覆盖不了、每次加分支都要改代码。为什么不一次让模型输出完整计划？→ 计划会与事实脱节，必须有 replan。
3. **线上坏了怎么定位**：看 trace 定位"第几步开始偏离"；动作签名重复 → 提示词/工具返回值有问题；步数均值上移 → 上下文或工具变慢变差；成本突增 → 单步 token 或调用数变化。
