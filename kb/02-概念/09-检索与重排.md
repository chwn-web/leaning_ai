# 检索与重排：召回是天花板，rerank 只能在天花板下面排序

**① 一句话定义**
从大量候选里，把**最相关的少数几条**排到前面并送进上下文。两件事分开看：**召不召得回**（recall）和 **排得对不对**（precision/排序质量）。

**② 它解决什么问题**
单路检索各有盲区：关键词检索精确但不懂同义，向量检索懂语义但对 ID/型号/错误码不敏感，两边都拿回来又太多，需要一层精排。

**③ 关键机制**

| 手段 | 救什么 | 代价 |
|---|---|---|
| **BM25/关键词** | 精确词、型号、错误码、人名、代码标识符 | 不懂同义、跨语言差 |
| **向量检索** | 语义相似、口语化提问、跨表述 | 对精确 token 不敏感、对罕见实体差 |
| **混合检索** | 两路各取 100–200，**RRF 或加权融合** | 延迟上升、需要调权重 |
| **Cross-encoder 重排** | 把 20–50 条重新打分，显著提升 top-1~3 的相关性 | 最贵的一步（要 GPU/额外调用），只能用在少量候选上 |
| **父子块 / 邻块扩展** | 小块用来搜（精度高），大块用来喂（上下文完整） | 实现复杂度上升 |
| **查询改写** | 多轮指代、同义扩展、拆子问题 | 改写错了会把召回带偏 |

**关键不等式**：
```
召回率 ≥ 重排后的质量上限
→ 没召回的东西，rerank 再好也救不回来
→ 相似度分数 ≠ 正确性（0.9 分也可能是无关段落）
```

**③.5 代码检索 ≠ 文档检索（Coding Agent 必考，来自 2026 一手面经 T017）**

> 面试原话："让 Agent 理解一个大型仓库，不可能把几十万行代码全塞进 context，你怎么构建当前任务需要的 coding context？"

| 维度 | 文档检索 | 代码检索 |
|---|---|---|
| 相关性来源 | 语义相似为主 | **符号精确性优先**：函数名、类名、变量、错误码、路径 |
| 纯向量为什么不够 | —— | 标识符是低频 token，embedding 会被周围注释稀释；`getUserById` 与 `getUser` 在向量空间里几乎一样 |
| 必需的额外通道 | 可选 | **AST / 符号表**（定义-引用、import 图）、**调用链**（从入口反向找可达路径）、**最近改动**（git blame/diff 缩小嫌疑范围） |
| 上下文单位 | 段落（chunk） | **文件 / 函数级**，先定位再展开；展开时带签名与相邻调用点，不是整文件 |
| 验证方式 | recall@k on docs | recall@k on **files**：给定 issue 描述，看召回集合里有没有真正要改的文件 |

四路分工：**向量**捞"语义相近的实现/类似模块" · **关键词/正则**捞"精确标识符与报错信息" · **AST/符号**捞"定义与引用，防改错副本" · **调用链**捞"改动会波及谁"。
代价：索引构建要跑解析器（增量更新是难点）、多语言支持碎、误召回会浪费大量窗口——所以输出必须带**行号区间**，让模型只读需要的那几十行。

**④ 边界与代价**
- 检索指标（recall@k, MRR, nDCG）与业务指标（任务成功率）不是一回事：检索变好，答案未必变好（可能上下文变长、噪声变多）。
- rerank 增加延迟，线上要设延迟预算与降级策略（超时就退回融合排序）。
- 多语言/领域术语：通用 embedding 在垂直领域常常不如领域模型或 BM25 + 同义词表。

**⑤ 工程落点**
- `projects/_template/src/tools/builtin.ts` `search_docs` —— 简化的关键词打分（idf 加权），演示"检索段"的输入输出契约：`query → [{docId, span, score, text}]`
- P2 升级路径：`src/retrieval/bm25.ts` → `src/retrieval/vector.ts` → `src/retrieval/fuse.ts`（RRF）→ `src/retrieval/rerank.ts`
- 评测脚本要能分别跑 `recall@k` 与端到端成功率，**否则你不知道该调检索还是调生成**

**⑥ 面试追问（三层）**
1. **怎么衡量**：标注 query→相关 doc，算 recall@k、hit rate、MRR/nDCG；线上看"命中率、无引用回答占比、用户追问率"。
2. **为什么不用另一方案**：为什么不能只用向量？→ ID/型号/精确词会漏。为什么不用大模型直接读完所有候选？→ 成本与延迟；所以用 cross-encoder 精排少量候选。
3. **线上坏了怎么定位**：先看 recall@k 是否下降（索引/embedding/新数据）→ 再看 rerank 是否把相关块压下去（模型/权重）→ 最后看拼装是否截断。
