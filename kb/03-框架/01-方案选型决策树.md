# 方案选型决策树：先问"该不该"，再问"用哪种"

> 90% 的技术选型错误不是"选错了方案"，而是**根本不该用这个方案**。
> 这张图用在三个场合：需求评审、写设计文档、面试白板题的第一句话。

## 决策树 A：这个需求该不该让模型来做？

```
用户需求进来
│
├─ 规则能穷举、结果必须 100% 确定？
│   └─ 是 → 写代码。别用 LLM。（发票金额计算、状态流转、校验）
│
├─ 需要理解自然语言/非结构化内容？
│   ├─ 否 → 写代码
│   └─ 是 ↓
│
├─ 一次调用能解决（分类/抽取/改写/摘要）？
│   └─ 是 → **单次调用 + 结构化输出**。不要上 Agent。
│
├─ 需要外部知识/私有数据？
│   └─ 是 → 加 **RAG**（检索 + 引用 + 无答案兜底）
│
├─ 需要多步、且步数根据中间结果变化？
│   ├─ 否（路径固定）→ **workflow**（代码编排，可控可测）
│   └─ 是 ↓
│
├─ 需要改真实世界（写库/发消息/操作浏览器）？
│   └─ 是 → **单 Agent + 工具**，且写操作必须有确认与幂等
│
└─ 上下文装不下 / 要并行 / 要独立验证？
    └─ 才考虑 **多 Agent**（2–3 个 specialist，优先于 5 个）
```

**反模式**（见到就警惕）：
- 用 Agent 做一个"查询天气"——workflow 一行代码的事。
- 用多 Agent 包装一个线性流程——加了 3 倍成本换来更难调的 bug。
- 用微调解决"知识更新"——模型参数不是数据库。
- 用 RAG 解决"模型不会推理"——检索补的是事实，不是逻辑。

## 决策树 B：知识从哪来？

| 知识特征 | 方案 | 理由 |
|---|---|---|
| 稳定、通用、已在模型里 | 不额外处理 | 别为模型已经知道的事付检索成本 |
| 会变、私有、需要引用/鉴权 | **RAG** | 可更新、可追溯、可按 ACL 过滤 |
| 固定风格/格式/领域语感，且样本充足 | **微调** | 学"怎么说"，不是学"事实" |
| 强约束的格式/取值 | **schema + 校验 + 工具** | 别指望模型自觉 |
| 少量规则性事实（< 20 条） | 直接塞进 system prompt | 检索是杀鸡用牛刀 |

口诀：**prompt 管行为，RAG 管事实，微调管风格，代码管正确性。**

## 决策树 C：编排形态怎么选？

| 形态 | 适合 | 不适合 | 关键代价 |
|---|---|---|---|
| 单次调用 | 分类/抽取/改写/摘要 | 需要多步或外部数据 | 无 |
| Workflow（代码编排） | 路径固定、要求可测、有明确阶段 | 长尾分支多 | 每加一种情况改一次代码 |
| 单 Agent 循环 | 步数不定、工具 2–5 个 | 工具 >10、成本极敏感 | 不确定步数、需要预算与循环检测 |
| Plan-and-Execute | 长任务、可分解、可并行 | 计划容易与事实脱节 | 必须支持 replan |
| 状态机 | 需要可恢复/可审计（审批、工单） | 开放式探索 | 建模成本高 |
| 多 Agent | 上下文隔离 / 并行 / 独立验证 | 线性任务、预算敏感 | 协调失败占大头（约 79%） |

## 一页速查：五类常见需求 → 推荐形态

| 需求 | 推荐 | 关键工程点 |
|---|---|---|
| 文档问答（内部知识库） | RAG + 单次调用 | ACL 预过滤、引用、abstain、recall@k 评测 |
| 客服工单自动分类+回复草稿 | 单次调用 + 结构化输出 + 人工确认 | schema 校验、置信度阈值、低置信转人工 |
| 数据分析助手 | Plan-Execute + SQL 工具 | 只读、查询超时、结果校验 |
| 浏览器自动化 | 单 Agent + 浏览器工具 + 沙箱 | 元素定位、等待重试、不可逆操作确认 |
| 多系统业务流程 | 状态机 + 单 Agent 辅助 | 幂等、补偿、审计、超时即"未发生"要核对 |

## 自检三问（写完设计先问自己）

1. **如果模型今天变笨 10%，这套方案会怎样？** 会崩 = 你把正确性押在模型上了。
2. **如果明天要换成另一家模型，要改几个文件？** >3 个 = 抽象没做对。
3. **怎么知道它变差了？** 答不出 = 没有评测，等于没上线。
