# 设计文档模板：一页纸，写不清就别写代码

> 用在三个场合：①每个项目开工前 ②面试白板题 ③给同事讲方案。
> **面试官不会看你写得多漂亮，他会看你有没有写"非目标"和"失败怎么办"。**

## 模板（复制这段用）

```markdown
# 设计：<一句话说清做什么>

## 1. 背景与目标
- 谁在用、什么场景、现在怎么凑合解决的
- 目标（可量化）：例如"内部文档问答，任务成功率 ≥ 85%（n≥100），p95 延迟 < 8s"

## 2. 非目标（明确不做什么）
- 例：不做多轮闲聊；不支持扫描件 OCR；不做跨租户共享

## 3. 约束
- 技术：模型只能用哪几家的哪几个；不能引入 X 依赖
- 业务：预算 ≤ $X/月；必须可审计；数据不能出境
- 团队：几周、几个人、谁维护

## 4. 方案对比（至少 2 个）
| 方案 | 怎么做 | 优点 | 代价 | 结论 |
|---|---|---|---|---|
| A | | | | ✅ 选它 |
| B | | | | ❌ 因为… |

## 5. 架构（套七层图）
- L6 体验：…  L5 编排：…  L4 上下文：…
- L3 模型：…  L2 工具：…  L1 数据：…
- L0 横切：评测 / trace / 权限 / 成本

## 6. 数据与权限
- 数据从哪来、谁有权、ACL 在哪一层生效（必须写"检索期过滤"）
- 删除与保留策略

## 7. 评测与指标
- golden set 规模与分层；主指标；门槛；怎么跑（CI/手动）
- 上线后看哪四个数（任务/模型/工具/体验）

## 8. 失败与兜底
- 模型超时/限流 → 降级方案
- 工具失败 → 重试/改计划/转人工
- 不可逆操作 → 确认与补偿
- 最坏情况：什么时候必须停下来交给人

## 9. 里程碑与回滚
- 分几步上线（灰度比例）；怎么回滚；回滚判据

## 10. 开放问题
- 还没想清的 1–3 条（面试时主动说出来，比装作全懂强）
```

## ADR（架构决策记录）模板：每个反直觉的决定留一条

```markdown
# ADR-000N：<决定>

- 状态：提议 / 已采纳 / 已废弃（被 ADR-000M 取代）
- 日期：

## 背景
当时面对什么约束/痛点。

## 决定
我们决定 ……（一句话）

## 备选与理由
为什么不是另一个方案（这条最重要，半年后只有它还有价值）。

## 后果
变好的地方 / 变差的地方 / 以后想改要先动什么。
```

`projects/_template/docs/adr/` 里已有两条示例：
- `0001-layering.md` —— 为什么分六层、为什么工具结果当不可信数据
- `0002-error-taxonomy-retry.md` —— 为什么错误分六类、为什么只有 transient 重试

## 三种典型写坏的设计文档

| 症状 | 后果 | 怎么修 |
|---|---|---|
| 只有架构图，没有指标 | 做完无法证明有用，评审过不了 | 第 1 节必须可量化，第 7 节必须给门槛 |
| 没有"非目标" | 范围无限膨胀，永远做不完 | 强制写 3 条不做的事 |
| 没有"失败怎么办" | 上线第一周就被一个超时打穿 | 第 8 节逐条列降级路径 |

## 一页纸的最小版（时间只够写 15 分钟时）

至少写这四行，也比不写强：
1. **目标（带数字）**：
2. **不做什么**：
3. **主方案 vs 备选（一句话各自的代价）**：
4. **怎么知道它坏了**：
