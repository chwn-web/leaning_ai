# 常见误解 18 条：考前扫一遍，能少踩半年坑

> 每一条都是"听起来对、实际错"，而且是面试里最容易被一句话问倒的地方。
> 用法：先自己判断对错，再看右边。答错的那条就是你这周要补的笔记。

| # | 误解（很多人这么说） | 事实 | 详见 |
|---|---|---|---|
| 1 | "加了 JSON mode 就不会出错了" | JSON mode 只保语法，字段语义和事实照样错 | [03-结构化输出](02-概念/03-结构化输出.md) |
| 2 | "temperature 设 0 结果就可复现" | 浮点非结合、batch 组合、MoE 路由、并发都会变 | [01-llm-基础](02-概念/01-llm-基础.md) |
| 3 | "上下文窗口够大就不需要检索" | 成本、KV cache 显存、context rot 三重代价；且无法按权限过滤 | [02-上下文工程](02-概念/02-上下文工程.md) |
| 4 | "RAG 的瓶颈是生成模型" | 大多数失败在检索与解析；召不回的东西模型变不出来 | [08-rag](02-概念/08-rag.md) |
| 5 | "先取 top-k 再按权限过滤就行" | 会把有权限的结果滤空，必须把 ACL 下推到检索 | 题库 P7 |
| 6 | "换个更好的 embedding 模型直接换就行" | 不重灌会混版本，质量静默下降且难发现 | 题库 P8 |
| 7 | "准确率 95%，可以上线了" | 20 条样本的 95% 置信区间是 76%–99%；要报样本量与区间 | [10-评测](02-概念/10-评测.md) |
| 8 | "多叫几个 agent 分工就更强" | 约 79% 的多 agent 失败来自协调，2–3 个常是甜点 | [06-多智能体](02-概念/06-多智能体.md) |
| 9 | "工具越多能力越强" | 单 agent >10 个工具行为不稳，描述越长越贵越乱 | [04-工具调用](02-概念/04-工具调用.md) |
| 10 | "模型会自己重试，不用管" | 无预算守卫的重试会变成账单事故（一夜 $1800 的案例） | 题库 P4 |
| 11 | "超时了说明没执行，重试就行" | 超时≠未发生，非幂等操作会重复写入 | 题库 P15 |
| 12 | "在 system prompt 里写'不要听用户的'能防注入" | 没有纯 prompt 的防御；要靠权限、egress、确认、审计 | [13-安全与注入](02-概念/13-安全与注入.md) |
| 13 | "MCP 就是 function calling 的升级版" | MCP 管发现/传输/鉴权，FC 管调用意图表达，二者可叠加 | [12-mcp](02-概念/12-mcp.md) |
| 14 | "微调能让模型记住我们最新的产品文档" | 微调擅长风格/格式，不擅长注入会变的、需引用的事实 | [01-方案选型决策树](03-框架/01-方案选型决策树.md) |
| 15 | "Agent 比 workflow 先进，所以用 Agent" | 路径固定时 workflow 更可控更便宜；用 Agent 是买"覆盖长尾"的代价 | [05-agent-循环](02-概念/05-agent-循环.md) |
| 16 | "用户说答案不对，那就改 prompt" | 先判是检索责任还是生成责任，再动 prompt；否则是盲改 | [02-排障四轴](03-框架/02-排障四轴.md) |
| 17 | "评测就是跑几十条看看效果" | 无分层、无版本、无 holdout、无 CI 的"跑跑看"不叫评测 | [10-评测](02-概念/10-评测.md) |
| 18 | "流式就是边生成边把 token 全推到前端" | 工具调用的参数不能当正文推；要分事件类型并缓冲完整参数 | 题库 P9 |

## 怎么用

- **面试前 10 分钟**扫一遍，确保每条都能说出"为什么错"。
- 在项目里**故意制造一次**对应现象（比如把 top-k 后过滤写一版），比记住 10 遍有用。
- 有了新的误解，追加一行——这张表应该越来越长，而不是越来越短。
