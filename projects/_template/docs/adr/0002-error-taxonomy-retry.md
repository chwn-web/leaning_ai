# ADR 0002：错误分 6 类，只有 transient 可以重试

- 状态：已采纳
- 日期：2026-11
- 决策者：项目作者

## 背景

最初的写法是 `catch (e) { console.log(e); return "出错了" }`。它有两个后果：

1. **该重试的不重试**：一次 429 就让整轮失败，用户看到"服务异常"。
2. **不该重试的疯狂重试**：参数校验失败也被重试，于是同一笔写操作被执行 N 次。

真实事故里最贵的不是模型答错，是**重试风暴**：一个有 bug 的循环一晚上重试 312 次，
账单 $1,800；另一个例子是 11 天烧掉 $47,000（题库 P4）。

所以必须回答一个问题：**这个错误值不值得再来一次？** 答案不能靠读错误字符串猜。

## 决定

所有错误在进入上层之前归一化成 6 类（`core/types.ts` 的 `ErrorCategory`）：

| 分类 | 含义 | 重试 | 典型来源 | 给用户看什么 |
|---|---|---|---|---|
| `transient` | 短暂故障，重试可能成功 | ✅ 指数退避 + 抖动 | 429/5xx/超时/连接重置 | "正在重试" |
| `permanent` | 确定性失败，重试没用 | ❌ | 404/解析失败/未知工具 | "无法完成，请联系人工" |
| `policy` | 业务规则不允许 | ❌ | 写操作缺确认/缺幂等键 | "需要你确认后我才能做" |
| `permission` | 没权限 | ❌ | 401/403 | "你没有访问权限" |
| `validation` | 参数不合法 | ⚠️ 交给模型修 | schema 校验失败 | （不进用户视野，回填给模型） |
| `budget` | 超出预算 | ❌ | 步数/成本/墙钟 | "任务太长，已停止并保留进度" |

### 三条配套规则

1. **重试只发生在边界处**：provider 层重试 HTTP，registry 层重试工具调用。业务层不再重试，避免"重试套重试"变成 N² 次。
2. **重试必须有上限和退避**：`withRetry({ maxRetries: 2, baseMs: 50, maxMs: 500 })` + 抖动。上限来自"用户能容忍等多久"，不是拍脑袋。
3. **校验错误不进重试，而是回填**：`validation` 的 observation 要写清字段名、期望类型、实际值（`core/validate.ts` 一次报全部错误），让模型自己修。

## 后果

**好的**：

- 一次 429 不会打断用户任务（S1/S2 里看不到，但 provider 层已经兜住）；
- 写操作不会因为重试而重复执行（`create_ticket` 的幂等键 + `isWrite` 双重保护）；
- 每一类错误都有对应的用户话术，不再出现"出错了"。

**代价**：

- `categorize()` 是猜的，遇到没见过的错误会落到 `permanent`（保守选择：宁可少重试，不可多花钱）；
- 多了一层"错误对象"，团队新人容易直接 `throw new Error()` 绕过分类——需要 code review 卡住。

## 一个具体判断：超时不代表没发生

`tool timed out after 5000ms` 属于 `transient`，可以重试。但这只对**读操作**成立。

对写操作，超时可能意味着"服务端已经执行了，只是响应丢了"。所以：

- 写工具必须有幂等键，重试才安全；
- 没有幂等键的写操作，超时应该**报错交给人确认**，而不是自动重试。

这条判断决定了 `registry.execute()` 里 `isWrite && !idempotencyKey` 必须**在调用 handler 之前**拒绝。

## 备选方案与为什么没选

| 方案 | 否决理由 |
|---|---|
| 用 HTTP 状态码直接判断 | 只覆盖网络错误，工具内部业务错误没有状态码 |
| 用错误消息字符串匹配 | `err.message` 会变（供应商改文案就失效），且无法区分语义 |
| 全部重试 3 次 | 参数错误重试 3 次 = 浪费 3 倍 token，且写操作有重复风险 |
