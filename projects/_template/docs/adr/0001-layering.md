# ADR 0001：按"七层"分层，依赖只能从外向内

- 状态：已采纳
- 日期：2026-11
- 决策者：项目作者

## 背景

前端转 Agent 最常见的失败模式是"一个 `chat.ts` 里同时有：拼 prompt、调 API、解析 JSON、
执行工具、写日志、算成本"。它能跑起来，但遇到三个问题：

1. **改不动**：想换模型供应商要动业务代码；想加 trace 要改每个函数。
2. **测不了**：没有网络就跑不起来，于是"评测"只能靠手动点。
3. **说不清**：面试官问"工具参数校验在哪一层"，答案只能是"在代码里某处"。

## 决定

把一次 agent 运行拆成七层，**依赖方向只允许 L6 → L5 → L4 → L3 → L2 → L1，L0 被所有层引用但不引用任何层**：

| 层 | 本骨架中的位置 | 职责 | 禁止做的事 |
|---|---|---|---|
| L6 体验 | （暂无，未来加前端） | 流式、进度、确认、重试按钮 | 直接调工具 |
| L5 编排 | `agent/loop.ts` | 循环、停止条件、死循环检测、状态 | 解析 HTTP、校验参数 |
| L4 上下文 | （暂无，见 kb/02-概念/02） | 拼装、压缩、记忆 | 调模型 |
| L3 模型 | `llm/provider.ts` | 协议、超时、重试、usage | 决定调用哪个工具 |
| L2 工具 | `tools/*`、`core/validate.ts` | 注册、校验、执行、幂等 | 拼 prompt |
| L1 数据 | `tools/builtin.ts` 的检索部分 | 解析、切分、过滤 | 调模型 |
| L0 横切 | `core/{types,errors,budget}.ts`、`obs/`、`eval/` | 类型、错误、预算、trace、评测 | 依赖任何具体层 |

`core/types.ts` 只放类型、不 import 任何模块，就是为了**打断循环依赖**：
其它六层都依赖它，它谁也不依赖。

## 后果

**好的**：

- 换 provider 只改 `main.ts` 一行构造；
- 加 trace 只在 registry/loop 的两个位置埋点，业务代码 0 改动；
- 评测可以在零网络下跑（`MockProvider` 就是为此存在）；
- 面试时每一层都能指到一个文件 + 行数。

**代价（必须承认）**：

- 文件比"一个大文件"多，初读成本高；
- 层间传递的接口（`ToolResult`、`RunResult`）必须先设计好，改起来牵连广；
- 有些逻辑天然跨层（比如"工具结果要不要截断"），必须选一边并写清理由——本项目选 L2，因为截断长度取决于下游模型窗口。

## 备选方案与为什么没选

| 方案 | 否决理由 |
|---|---|
| 单文件（500 行 `agent.ts`） | 能跑，但无法回答"这层在哪"，也无法局部测试 |
| 依赖 LangChain 的分层 | 分层是别人的，被追问时只能说"框架就是这样" |
| 按"功能"分（聊天/检索/工单各一套） | 三个功能会复制三套 loop，改一处要改三遍 |

## 如何验证这个决定是对的

- 从 `_template` 复制出 5 个不同项目（P0–P4），**loop.ts / registry.ts / budget.ts 是否都没改**；
- 如果某个项目不得不改 loop，说明"编排"里混进了业务，要把它挪到工具或上下文层。
