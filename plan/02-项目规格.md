# 项目规格（Projects Spec）

> 原则：**先写 README 再写代码**。README 里必须包含"验收标准"，达不到就缩范围，不许延期。
> 每个项目都要能回答三件事：解决谁的问题、技术上最难的点是什么、你怎么知道它有效。

## 开工方式（所有项目通用，别自己从零搭）

每个项目都从 [`projects/_template`](../projects/_template/README.md) 复制，只改 3 个文件：

```powershell
Copy-Item -Recurse projects/_template projects/p1-tool-agent
```

| 改哪个 | 改成什么 | 不用动的（这是骨架的价值） |
|---|---|---|
| `src/tools/builtin.ts` | 这个项目的真实工具 | `agent/loop.ts`、`tools/registry.ts`、`core/*`、`obs/tracer.ts`、`eval/*` |
| `src/main.ts` | 真实业务流程（替换 5 个 demo 场景） | |
| `data/golden.jsonl` | 本项目的 30+ 条真实用例（**先写用例**） | |

七层骨架与"改哪 3 个文件"的完整说明见 [`kb/03-框架/03-统一项目骨架.md`](../kb/03-框架/03-统一项目骨架.md)。
如果某个项目不得不改 `loop.ts`，先停下来判断：是骨架不适用，还是你把业务逻辑塞进了编排层。

## P0 · 多模型网关（W1–W2，12h）

**定位**：打底项目，不一定写进简历，但后面所有项目都依赖它。

**做什么**
- 统一入口 `/v1/chat`：鉴权、模型路由、流式透传
- 接 3 家模型（建议：OpenAI 或兼容协议 + DeepSeek + 阿里 Qwen/智谱）
- 失败策略：超时（8s 首 token）/ 429 / 5xx → 指数退避 → 降级到备用模型
- 计量：每次请求记录 input/output tokens、耗时、估算费用、命中缓存与否
- 极简 Web UI：模型下拉、多轮对话、实时显示 token/费用/首 token 延迟

**非目标**：不做多租户、不做计费结算、不做管理后台。

**技术栈**：TypeScript + Node（你熟），一个 Python FastAPI 对照服务（练手，为后面 RAG 铺垫）。

**目录**
```
projects/p0-llm-gateway/
├── README.md          # 含验收标准
├── server/            # 网关
│   ├── providers/     # 每家一个 adapter，统一接口
│   ├── router.ts      # 降级与路由
│   └── metering.ts
├── web/               # 极简前端
└── bench/             # 比价脚本
```

**验收**
- [ ] 拔掉主供应商网络（或改错 key）后，请求自动降级，前端无感
- [ ] `/metrics` 能查到每家模型 7 日的 token 与费用
- [ ] 比价报告：10 个问题上 3 家模型的成本/延迟/质量打分

**面试讲法**：不说"我做了个网关"，说"我给团队做了一层模型抽象，把切换成本从 2 天降到 10 分钟，月成本降了 X%"。

## P1 · 工具型 Agent（W3–W9，45h）

**定位**：简历主项目 1，证明你懂 Agent 循环而不是只会调 API。

**做什么**
- 工具集：`read_file` / `write_file` / `search_web` / `http_request` / `run_code(沙箱)` / `git_diff`
- 循环保护：max steps（默认 25）、token 预算、重复调用检测（相同工具+参数 3 次即中断）、总超时
- 记忆：会话内短期记忆 + 跨会话的"任务档案"（做过什么、失败在哪）
- HITL：写文件 / 执行代码 / 发请求前弹审批，可编辑参数
- 前端（**你的差异化**）：时间线视图展示 思考→工具调用→结果→下一步，显示每步耗时/token，支持暂停/打断/回滚到某一步

**难点（面试重点）**
1. 流式与工具调用并存：工具参数是增量 JSON，需要容错解析 + 未完成时不可执行
2. 循环检测：语义重复 vs 字面重复
3. 错误恢复：工具报错要变成"模型能用的信息"，而不是抛栈
4. 中断与恢复：暂停后状态要可序列化

**目录**
```
projects/p1-tool-agent/
├── README.md
├── agent/
│   ├── loop.ts          # 核心循环（先写裸的，别上框架）
│   ├── tools/           # 每个工具带 schema + 校验 + 错误规范
│   ├── guard.ts         # 步数/预算/循环检测
│   └── state.ts         # 可序列化状态
├── sandbox/             # 代码执行隔离
└── web/                 # 时间线 UI
```

**验收**
- [ ] 10 个复杂任务跑通率 ≥70%（任务清单写进 README）
- [ ] 注入故障（工具超时/返回乱码/权限拒绝）后自恢复率 ≥80%
- [ ] 前端能看到每次工具调用的入参/出参/耗时
- [ ] 能说清"为什么这里不该上多智能体"

**面试讲法**：重点讲**你踩的坑和修法**，别讲功能列表。"我们发现 40% 的失败是模型重复调用同一工具，于是加了语义去重 + 强制换策略提示，失败率降到 12%。"

## P2 · 知识库 Agent（W10–W15，50h）

**定位**：简历主项目 2，**面试最高频方向**，必须带数据。

**做什么**
- 文档接入：PDF/Markdown/网页 → 解析（含表格、图片 OCR）→ 三种切分策略可选
- 检索：BM25 + 向量混合，RRF 融合，可插拔 rerank
- 生成：强制引用（回答里带 `[docId#chunkId]`）、无依据拒答
- 前端：答案旁列出引用片段，点击定位原文高亮
- **评测**：≥100 条评测集（问题/标准答案/证据），一键回归输出指标表

**实验矩阵（必须有数据）**
| 变量 | 取值 |
|---|---|
| 切分 | 512 固定 / 语义 / 父子块 |
| 检索 | 纯向量 / BM25 / 混合+RRF |
| 重排 | 有 / 无 |

→ 输出 3×3×2 的指标对比，写进博客。

**目录**
```
projects/p2-rag-agent/
├── README.md
├── ingest/        # 解析 + 切分
├── index/         # 向量库 + BM25
├── retrieve/      # 融合 + rerank + 改写
├── generate/      # 引用 + 拒答
├── eval/
│   ├── dataset.jsonl   # ≥100 条
│   └── run_eval.py     # 一键回归
└── web/
```

**验收**
- [ ] 一条命令跑完评测，输出 命中率/MRR/忠实度/拒答准确率
- [ ] 能说清每个指标提升来自哪个改动（消融）
- [ ] 无依据时拒答率 ≥90%，同时误拒率 ≤10%
- [ ] 博客发布，带真实数字

**面试讲法**：面试官最爱问"你怎么知道它变好了"。你要能掏出评测集和对比表。这是 80% 候选人拿不出的东西。

## P3 · 可视化 Agent 平台（W16–W21，60h）

**定位**：简历主项目 3，拉开差距，也是系统设计题的素材库。

**做什么**
- 编排：配置式/节点式定义 Agent（模型、工具、提示、终止条件、审批点）
- 执行：队列 + 并发控制 + 检查点（可中断恢复）+ 时间旅行
- 可观测：trace 树（run → step → tool call），成本归因，失败率看板
- MCP：实现 1 个 Server（内部知识/工单），支持鉴权与限流
- 安全：工具白名单、参数校验、间接注入检测、敏感操作二次确认
- 部署：容器化 + 多租户隔离（至少逻辑隔离）

**目录**
```
projects/p3-agent-platform/
├── README.md          # 带架构图
├── docs/architecture.md
├── server/            # 编排引擎 + API
├── workers/           # 任务执行
├── mcp-server/
├── web/               # 编排界面 + trace 查看 + 成本看板
└── deploy/
```

**验收**
- [ ] 任一运行 30 秒内定位：耗时分布、token 分布、失败步骤
- [ ] 中断后可恢复，且能从任意检查点重跑
- [ ] 20 个红队用例拦截率 ≥85%
- [ ] 开源，README 有架构图 + Demo GIF，≥1 个外部用户试用

**面试讲法**：当成"我设计过一个 Agent 运行时"来讲：状态怎么存、失败怎么兜、成本怎么控、权限怎么管。

## P4 · 垂直场景产品（W22–W24，45h）

**定位**：记忆点。面试官记不住仓库，记得住产品。

**选型原则**
1. 你有领域知识（前端工程、测试、文档、招聘、电商…任选）
2. 痛点真实且高频
3. 2 周能做出 MVP，不依赖重运营
4. 有"Agent 才做得到"的部分，不是套壳聊天

**你的答案：审核 / 审批类（首选）**——你在 TCL 做的正是"AI 自动审核 + 自然语言→数据库查询→图表"这类业务，领域知识、真实痛点、可量化收益三样都现成，不需要现找场景。

| 方向 | 为什么适合你 |
|---|---|
| **🅰 单据/影像审核 Agent（首选）** | 你天天在校验"AI 自动审核"准不准：能讲清审核口径、误判代价、人工兜底、抽检比例；这是**别人编不出来的真实性** |
| 🅱 自然语言取数 Agent（备选） | 你的"光伏智擎"就是这个形态：NL→SQL→图表→追问，天然带权限与口径治理问题 |
| 🅲 前端仓库巡检 Agent | 你懂前端工程化：依赖升级、死代码、可访问性、性能回归 |
| 🅳 设计稿转代码 + 视觉回归 | 演示效果炸裂，但和 Agent 工程深度关系弱，优先级最低 |

**审核类为什么是最优解（面试视角）**：它天生包含 Agent 面试最爱的四个硬问题——**判定标准由谁定**（口径与规则）、**判定错了谁负责**（人机协同与兜底）、**怎么证明变好了**（抽检样本 + 一致率 + 置信区间）、**权限与审计**（谁能看、谁改了、留没留痕）。这四个问题在纯 Demo 项目里没有，在审核业务里有。
**红线**：只能用公开或自己构造的数据，禁止把公司真实数据/内部系统截图放进仓库和简历；讲的时候说"脱敏后的同类场景"，不说具体客户与单据内容。

**做什么**
- 真实域名上线，接真实用户，埋点（谁在用、用了几次、失败在哪）
- 迭代一版：根据 10 个反馈砍功能、修最痛的三处
- 写"产品复盘"：定位、指标、失败决策

**验收**
- [ ] 有 URL、有 ≥10 个真实用户、有使用数据
- [ ] 能讲清"为什么这个场景需要 Agent 而不是普通自动化"
